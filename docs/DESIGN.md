# Design decisions

The goals of `cq`, the implementation choices that the specification left open, and what `cq` does. The original specification is in [`SPEC.md`](SPEC.md). It is historical: where it differs, this page and [Commands](COMMANDS.md) describe what `cq` does now. Back to the [README](../README.md).

## Goals

The [README](../README.md#goals) lists these goals in short. This section gives the reason for each, and the choices that follow from it.

### Hand-offs without a person

Sessions hand work to each other without a person prompting them.

- **Why.** A hand-off between coding sessions usually needs a person, to pass the message on or to prompt the receiving session. Built-in messaging can also stop for a person: Claude Code's cross-session messages stop after 10 in a row.
- **So.** Each session has a watcher that starts the receiving session's turn when a message arrives. A message is a file that any agent can read and claim with `cq`, so a session of one agent can hand work to a session of another.
- **Limit.** The goal holds only when a turn can run `cq` with no approval prompt. A turn that waits for an approval handles nothing until a person answers. Each agent's setup page says how to allow `cq`. For Codex, a setup with no approval prompt is not tested yet.

### No idle checks

No model turns are spent checking an empty queue.

- **Why.** A model turn reads the session's context again, so a check that finds nothing still costs tokens. A 10-minute Codex automation cost about 1% of the 5-hour limit per run, with an empty inbox (see [Codex wake](#codex-wake)).
- **So.** `cq` does the waiting itself. The inbox, `--to-codex` and `--to-agy` watchers, and `cq dispatch`, are plain processes that start a model turn only when there is a message.
- **Exceptions.** Monitor mode: the session re-arms the watcher at least every 30 minutes, and each re-arm is a model turn (see [Inbox mode](#inbox-mode)). Scheduled polling: each run is a model turn, even with an empty inbox. Both are fallbacks.
- **Limit.** The goal is about model turns, not total cost. A watcher still uses some CPU and memory, and each handled message costs a model turn in every mode (see [Cost of an idle session](OVERVIEW.md#cost-of-an-idle-session)).

### Quick pick-up

A message is read soon after it is sent.

- **Why.** Work that waits for a hand-off cannot go on until the receiver reads the message.
- **So.** A watcher reacts to file-system events. A timed rescan is only a backup (see [Watcher](#watcher)).
- **Trade-off with no idle checks.** The inbox, `--to-codex` and `--to-agy` watchers hold new lines for 2 seconds, so a burst of messages costs one turn, not one per message. The inbox and `--to-codex` watchers also keep posts 5 seconds apart. This adds a few seconds of delay.
- **No target.** The goal has no number. The observed delays are in the README's [support table](../README.md#support-by-agent-and-surface), with the evidence in [Test status](TESTING.md).

## CLI and exit codes

- Exit codes are as in the table in [Commands](COMMANDS.md#exit-codes). No general error uses exit 1, because a session treats `claim` exit 1 as "already handled". Clap's own usage errors (normally exit 2) are mapped to 64, because 2 means a rename failed.
- `cq init` creates the layout. Every other command refuses to run (exit 70) until it has. Per-name directories are created on demand.
- `CQ_ROOT` must be absolute. A relative path is refused, so that sessions in different worktrees cannot end up with different queues.
- `config.toml` in the queue root holds `rules`, `tz` and `tz_label` (6 Nov 2026). The order for each is: environment variable, the file, the build's default, the built-in default. The file cannot set the root, because `cq` finds the file in the root. All data and settings can then live in the per-user default root, and no path needs baking into the build.
- A problem in `config.toml` gives a warning, never an error (6 Nov 2026). A typo such as `tz_lable` must not stop the queue for every session. `cq` prints one warning on stderr that names the file and each problem. It ignores an unknown key or a wrong value and keeps the other keys; a `tz` that is not a known zone gives way to the next source. A file that is not valid TOML is ignored whole. `cq-top` warns the same way. The hooks print the warning only with `--debug`, so a hook stays silent. An older `cq` also keeps working with a key that a newer one added.
- `config.toml` is trusted at the level of `coordinators` (11 Nov 2026, issue #83): any session can edit it, and `rules` steers every session start. So `rules` with a control character is ignored with a warning, and `tz_label` is printed without control characters or line separators and cut to 16 characters. A UTF-8 byte order mark is skipped; UTF-16 text is ignored whole with a warning.
- Values that other sessions can write and that `cq` prints in a line are checked (11 Nov 2026, issue #83): the `time` in a `.reason.json` file prints only as a UTC time, else `?`; a watcher record's `version` with a character other than letters, digits, `.`, `+` and `-` reads as unknown.
- `send` reads stdin only when it is not a terminal and `--input FILE` is not given. A leading UTF-8 BOM in the input is removed. Unknown input fields are refused (exit 64).
- `done` reads input only with `--reply` or `--reject`. With neither, it never reads stdin, so an open stdin pipe (as in Claude Code's Bash tool) cannot block it. It does check stdin without blocking, and refuses (exit 64, nothing moved) when input is waiting, so a reply given without `--reply` is never lost silently (seen live on 24 Oct 2026). Input is waiting when stdin is a pipe with bytes in it, or a non-empty file; Git Bash passes a small heredoc as a pipe and a large one as a temporary file. A console, `NUL`, a closed pipe, or an open pipe that stays empty for 100 ms counts as no input. On macOS and Linux, a non-empty file counts, and a pipe or socket counts when bytes arrive within 100 ms (Node.js, which runs Claude Code, uses socket pairs for child-process pipes). `--input` without one of the flags is refused (exit 64).
- `--reply` needs a non-empty `"reply"`; `--reject` needs a non-empty `"reason"` and allows neither `"reply"` nor `--status`. `--status` needs `--reply`. `--reply` and `--reject` cannot be combined.
- `--reply` on a `result` or `info` is refused (exit 5) before the move, so the message stays claimed. If the claimed file cannot be read, its type and sender are unknown: `done` moves it and sends nothing. With `--reply` or `--reject` it then exits 4, because the session asked for something that was not sent.
- `cq watch` has two hidden flags for tests: `--rescan-seconds` (default 60) and `--no-fs-events`.

## Messages

- Hop limit: a message that would have 5 hops is refused, so the highest stored value is 4. An answer is the exception and may have 5: a reply, rejection or notice sent by `cq done`, a DLQ notice sent by `cq claim`, and a `result` sent with `cq send --reply-to`. Without this, a task with 4 hops could never be answered. Nothing can follow an answer with 5 hops. With both `--parent` and `--reply-to`, hops is 1 + the higher of the two.
- `cq send --reply-to` must name a `task`. A reply to a `result` or `info` is refused (exit 5), as `cq done --reply` is. Use `--parent` to send a new message about a result or info.
- Replies sent by `cq done`, and DLQ notices sent by `cq claim`, take their hop count from the message they answer, without a lookup.
- The pair, recipient and sender limits count files by name (the time stamp and sender in the ID), across the inbox, `.processing/`, `done/`, `rejected/` and `dlq/` of the recipient (pair, recipient) or of every recipient (sender). The recipient is the directory name. Messages pruned after 14 days are long outside the 1-hour window.
- The checks run in this order: arguments, body size, `PAUSE`, hops, pair, recipient, sender. The first one that fails is reported.
- The recipient limit stops many senders flooding one session; the sender limit stops one session fanning out to many. Both were added on 24 Oct 2026.
- `PAUSE` refuses sends as well as silencing watchers, so a storm stops at the source. A `done --reply`, or a `--reject` of a task, under `PAUSE` still moves the message and exits 4 (reply not sent). A `--reject` of an info or result exits 0 and warns on stderr that the sender was not told. A `claim` that dead-letters a message still exits 3; its stderr line says the sender could not be told.
- The 20 KB limit is 20480 bytes of UTF-8 in `body` (and in a `done` reply or reason). The subject has no limit in the file; the event line shows at most 80 characters.
- Validation goes beyond the schema: `id` must match the file name, `to` must match the inbox, `created` must be RFC 3339 ending in `Z`, `reply_to` and `parent` must be IDs, a `result` needs a status, a `task` or `info` must have status null, and a file starting with a BOM is invalid.
- Schema: `reply_to`, `parent`, `status`, `from_session_id` and `from_host_session_id` are optional (null when absent). `cq` always writes every field.
- A DLQ notice (a `failed` result, subject `Not processed: <id>`) goes to the sender named in `from`, or, when the JSON is unreadable, to the sender named in the file's ID. It is sent for any message type, following the brief; the hop count and rate limit stop loops.
- Reply subjects: `Re: <subject>`, and `Rejected: <subject>` for a rejection. The body of a task's `rejected` result is the reason.
- Rejecting an info or result sends the sender an `info` notice ([issue #20](https://github.com/niklasrichardson/session-queue/issues/20)): `reply_to` is the rejected ID, and the body names the ID, the subject and the reason. It is an `info`, not a result, because only tasks get results. The reject is the main action, so a notice that a limit blocks only gives a stderr warning. Rejecting a `rejected` result or a notice sends nothing, so two sessions cannot reject back and forth; the hop limit is a second stop.
- `cq requeue` moves a message only from the session's own `rejected/` folder to its inbox, by rename, so the ID and contents stay the same. It sets the file's modified time to now, so the watcher announces it again and a coordinator's `CQ-WAKE` counts from the requeue. It holds the recipient's claim lock (`heartbeat/<name>.claim.lock`) until the reason file is removed, so a claim cannot start before then.
- `done` checks its input first, and for `--reply` the message type, and moves nothing if either is wrong. It then moves the file and sends the reply. If the reply cannot be sent, it exits 4 with the message already in `done/` or `rejected/`.
- Reason files are `<id>.reason.json` (`id`, `inbox`, `reason`, `time`), next to the message in `dlq/` or `rejected/`.
- Moves never replace an existing file. If a send's ID is already taken, `cq` picks a new random suffix (up to 5 tries).

## Watcher

- Any file-system event in the inbox triggers a full inbox scan. The scan decides what is new, so events never need parsing. If `notify` cannot start or stops, the watcher rescans every 5 seconds and says so on stderr.
- A message is announced once per watcher run. A restarted watcher announces every unclaimed message again, once; `cq claim` exit 1 makes repeats harmless. The watcher knows a message by its ID and modified time, so a message that `cq requeue` puts back (with a new modified time) is announced again, even when the claim, reject and requeue all happen between two scans.
- Only files whose name is a valid ID are announced or listed. A file with any other name cannot be claimed.
- The event time is when the watcher saw the message, not the `created` time.
- Unreadable `from` or `type` fields show as `?` in event and list lines. Such a message still gets announced, so that `cq claim` can send it to the DLQ.
- While `PAUSE` exists, the watcher announces nothing and remembers nothing. When `PAUSE` goes, it scans at once.
- The loop ticks every 250 ms (clock, `PAUSE`). Heartbeat at start and every 30 seconds; the file holds the time. Prune at start and every hour, by file modified time.
- `claim` sets the file's modified time to the claim time, so `list --stale-minutes` measures from the claim, and the prune measures from the claim too (a move keeps the modified time).
- Lock: `File::try_lock` on `heartbeat/<name>.lock`. The OS releases it however the process exits.
- `--takeover` reads the pid file, checks that the process is a `cq` executable (same file name as the running binary), terminates it, and waits up to 5 seconds for the lock. On macOS and Linux it sends SIGTERM, then SIGKILL if the process is still running after 5 seconds. It refuses to stop any other program.
- No parent check (removed 24 Oct 2026). Under the Monitor, the parent of `cq.exe` is a forked Git Bash (the Monitor runs `bash -c "... eval 'cq watch ...' < /dev/null && pwd -P ..."`), whose lifetime Cygwin controls, not the Monitor. The check was the only path that could end a watcher with exit 0 and no output while its Monitor still ran, which was seen 4 times. `--max-seconds 1790`, the single-instance lock and `--takeover` bound an orphan instead: it lives at most 30 minutes, and `--takeover` replaces it at once.
- T14 follows from this: after only the parent is killed, the orphaned watcher keeps running and a plain second `cq watch` exits 5; `--takeover` stops the orphan, and exactly one watcher runs. A separate test runs the watcher through three nested `bash -c ... eval` forms and checks that each runs to `--max-seconds`.
- The watcher exits 0 at `--max-seconds` or when stdout can no longer be written, and prints one line to stderr saying why (`cq watch: exiting: --max-seconds 1790 reached`). Every error exit prints `cq: <reason>`. It removes the pid file if the file still holds its own ID.
- The watcher exits 7 with `CQ-SLEEP` while its name is asleep (see [Sleep](#sleep)). Exit 7 is not an error, so it prints no `cq:` line.

## Inbox mode

`cq watch --to-inbox` posts the watcher's lines into the session's own Claude Code inbox instead of stdout. The commands are in [Commands](COMMANDS.md#watch-into-the-inbox) and the session steps in [Protocol](PROTOCOL.md#inbox-mode).

- **Decision (28 Oct 2026).** Inbox mode is the default way for Claude Code sessions to receive queue events. Monitor mode is the fallback, for a session where `--to-inbox` exits 64 (no inbox). Inbox mode was added as experimental in [#24](https://github.com/niklasrichardson/session-queue/pull/24). On 28 Oct 2026 the owner moved all live sessions to it, to test it in real use. A planned 24-hour soak test was stopped after about 1 hour, so there are no long-run results yet.

- **Why.** Under the Monitor, the watcher must be re-armed at least every 30 minutes, because the Monitor expires. Each re-arm is a model turn that reads the whole context again. An idle session pays for 2 re-arms an hour for nothing. A watcher that posts into the inbox can run for hours, and the session pays only for turns that have queue events.
- **The documented path.** Claude Code gives each session an inbox and exports its address and a token to the session's Bash commands and hooks ([The session's inbox socket](https://code.claude.com/docs/en/cross-session-messaging.md#the-sessions-inbox-socket)). It delivers a message from the session's own child process, and a message to an idle session starts a new turn. On Windows the token in the auth line is the only proof that the poster is a child of the session, so `cq` always sends it. The owner tested this live on 28 Oct 2026: a background child posted after 180 seconds and woke an idle session.
- **Batching.** Claude Code refuses rapid bursts to one inbox and drops identical repeats, and each message to an idle session costs a turn. So `cq` holds lines for 2 seconds and keeps posts 5 seconds apart. The burst limit is not documented, so 5 seconds is a guess. A post holds at most 50 lines.
- **One last message.** A watcher that stops posts why, with any held lines, in one message, so the session knows to re-arm (or, when asleep, not to). One message costs one turn, not two. Exit 7 and `CQ-SLEEP` keep their meaning.
- **Exit 8.** A post that still fails after 4 tries over about 7 seconds means the inbox is gone, which means the session has ended. The watcher stops, so it never runs on without a reader. It is a new code because sessions act on exit codes, and none of the others fits.
- **No default `--max-seconds`.** The time limit only exists because the Monitor expires.
- **Signals.** The watcher catches SIGTERM, so on macOS and Linux a watcher replaced by `--takeover` posts a stopped message. If it is still posting 5 seconds later, `--takeover` sends SIGKILL and the message can be lost. On Windows, `--takeover` uses `TerminateProcess`, which cannot be caught, so the old watcher posts nothing.
- **Transport.** A named pipe opened with `std::fs::OpenOptions` on Windows, and `std::os::unix::net::UnixStream` elsewhere, in `src/platform.rs`. No new dependency. The tests' fake inbox needs the `Win32_System_IO` feature of windows-sys, as a dev-dependency only.
- **Unknowns.** Whether the desktop app stops the processes of an idle session, and how long the inbox stays reachable. How Claude Code's Bash tool reports the watcher's exit next to the stopped message. A watcher whose session ended without stopping it finds out only at its next post; until then it holds the name and writes its heartbeat. Long runs (many hours) have not been tested.

### Known risks

- **A watcher that dies silently.** An inbox watcher posts a stopped message when its name is put to sleep, when it reaches `--max-seconds`, on an error, or (on macOS and Linux) on a signal. A watcher that is killed without warning posts nothing: for example, if the desktop app stops the session's processes. The session is not told, so it does not restart the watcher, and messages wait in its inbox. `cq send` does not warn the sender.
- **Monitor mode heals itself.** The Monitor expires at least every 30 minutes, and the session re-arms it. So a dead Monitor-mode watcher is replaced within 30 minutes. Inbox mode has no such timer.
- **How to spot it.** The watcher's heartbeat stops. [cq-top](CQ-TOP.md) shows it as `STALE` after 90 seconds. Since cq 1.11.0, `cq status --as NAME` exits 10 as soon as the process in the pid file no longer runs. After a `/clear`, `cq session-start` also tells the session that its inbox watcher has stopped. To restart it, run `/cq-start` in that session.
- **A watcher that posts to an old target ([#77](https://github.com/niklasrichardson/session-queue/issues/77)).** A watcher reads the inbox address and token once, at start. Claude Code can give the session a new token (seen after a resume). The old watcher then keeps its heartbeat, `cq status` says `running`, and its posts vanish without an error. The messages still wait in the inbox.

### Watcher record (cq 1.11.0)

- **Decision.** Each watcher and dispatcher writes `heartbeat/NAME.watcher` before its pid file: its process ID, its `cq` version and, in inbox mode, the inbox address and the first 16 hex digits of the SHA-256 of the token. The token itself is never written. A hash prefix is enough to tell two tokens apart, and the queue folder is readable by every session.
- **Trusted only with its pid file.** The record is used only when its `pid` matches `heartbeat/NAME.pid`. So a record left by an older watcher, or one that a new watcher has not replaced yet, is ignored. A pid file without a matching record means a `cq` older than 1.11.0: its version is `unknown`.
- **Session-start compares.** In inbox mode, `cq session-start` compares the record with the hook's own `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` and with its own version. Only a full match keeps the "still runs" text. Any difference, a missing record, or a hook without the variables gives the restart text with `--takeover`. A needless restart costs one background command; a stale watcher costs every message until someone notices.
- **Process check.** `cq status` and `cq session-start` also check that the process in the pid file still runs (`OpenProcess` and `WaitForSingleObject` on Windows, `kill(pid, 0)` elsewhere). Where the check cannot answer, only the heartbeat counts, as before. A reader treats its own process ID as dead, because Windows reuses process IDs at once.
- **Version as a signal.** `cq status` adds `version=`, `outdated` and `stale-target`, and cq-top shows the version, so a watcher left running across a `cq` upgrade is visible. These words never change an exit code, because sessions act on exit codes.
- **Unknowns.** Whether every hook gets `CLAUDE_CODE_MESSAGING_TOKEN` as Bash commands do has not been checked in a live hook. If it does not, session-start always asks for a restart, which is safe but costs a turn.
- **Exit log.** Each watcher that held the lock appends one line to `watch-exits.log` when it ends, with its reason. A watcher killed outright cannot, so the next watcher for the name writes the line for it when it finds the old pid file: a clean exit removes that file, and holding the lock proves the old process is gone, so no process check is needed. This turns a silent death into evidence after the fact. Under a Monitor on macOS and Linux no signal handler is installed: one that writes a file is not async-signal-safe, and catching the signal would change the exit status the Monitor sees (see [Watcher status and exit log](COMMANDS.md#watcher-status-and-exit-log)).

## Codex wake

`cq watch --to-codex THREAD` wakes an existing Codex Desktop chat with `codex queue`. The commands are in [Commands](COMMANDS.md#wake-a-codex-chat) and the setup in [Codex setup](agents/CODEX.md#wake-a-codex-chat-with-cq-watch---to-codex).

- **Why.** The fallback, a same-chat automation that runs every 10 minutes, costs a model turn per run even when the inbox is empty (about 1% of the 5-hour limit per run, [issue #12](https://github.com/niklasrichardson/session-queue/issues/12)). `codex queue` starts a turn only when there is work. Other routes were rejected in issue #12: the Desktop app's app-server is private, `codex exec resume` on a live chat can split its history, and hooks cannot start a turn.
- **A sink, like the inbox.** It reuses the watcher and its `Sink` trait, so the lock, heartbeat, `PAUSE`, sleep and `--takeover` behave as in every mode. It uses the inbox values for batching (2-second window, 5-second gap) and retries (4 tries, 1, 2 and 4 seconds apart). One Codex turn handles every `UNCLAIMED` message, so one call per batch is enough.
- **Fixed prompt.** Codex reads the queued message as a user instruction. Queue text is written by other sessions, so none of it goes into the message: not the subject, body, sender or ID. The chat reads its messages with `cq claim`, under its `AGENTS.md` rules.
- **No shell.** `cq` starts the Codex executable directly, with each argument separate, so no character in the thread name or prompt is interpreted.
- **Exit 9.** A call fails on a non-zero exit, on no `Queued message` line, or after 60 seconds. After 4 failed tries the watcher stops with a new code, because nothing wakes the chat any more and none of the other codes fits.
- **The loop never waits for Codex.** A call and its retries could take about 4 minutes. If the loop waited for them, it could not write the heartbeat (so `cq status` would call a live watcher stale after 90 seconds) or notice sleep and `PAUSE`. So, as with `--to-agy`, the watcher starts `codex queue` and checks on each tick whether it has ended. Each call runs in its own Job Object (Windows) or process group (Unix), so a call past 60 seconds is stopped with every process it started. A process left by a call that ended is left alone, as before.
- **A bounded last call.** On a normal stop the watcher waits at most 60 seconds for its last check: the same limit as one call, so a hung call is stopped as during the run, and calls that fail at once still get all 4 tries. On sleep it stops a running call at once, because the name must not be woken and the messages wait in the queue.
- **Its own member key.** The watcher usually runs in another process tree than the Codex chat, often started by a Claude Code session. Recording it under that session's key would replace the session's own name, so it uses `CQ_SESSION_ID` or `codex-NAME`.
- **Known risks.** `codex queue` is experimental. It confirms that the message is stored, not that a turn started. A message queued while the app is closed is untested ([issue #25](https://github.com/niklasrichardson/session-queue/issues/25)). The chat is not told when its watcher stops; cq-top shows the heartbeat.

## Antigravity CLI wake

- **A turn is a process tree.** `agy` starts helpers and shell commands. Each turn runs in its own Job Object (Windows) or process group (Unix), so the 30-minute limit stops all of it, not only `agy`. The Windows job has no kill-on-close, unlike the dispatcher's: a turn that still runs when the watcher stops must finish on its own. Only the time limit stops a turn.
- **No session variables.** `agy` gets neither the inbox variables nor the session variables that the dispatcher clears (`CQ_SESSION_ID`, the Codex thread and session IDs, the Claude Code session IDs). One helper, `members::remove_session_vars`, clears them for the dispatcher, `--to-agy` and `--to-codex`.

## Antigravity CLI broker mode

Windows only in 1.15.0: on other systems `--agy-broker` is a usage error (exit 64). The problem it fixes (Low integrity, Mandatory Integrity Control) is Windows only, and the Unix exchange folder needs trust checks that read ACLs first (see the Unix trust boundary below). The Unix exchange code and its unit tests stay, built and run in CI.

- **The finding.** On Windows, an `agy` turn runs at Low integrity in a sandbox. The queue root is Medium, and Windows does not let a Low process write up. So a turn cannot run `cq claim`, `cq done` or `cq send`.
- **The root stays Medium.** Lowering the queue root's label would let every Low process on the machine write the queue. Instead, `--agy-broker` makes the watcher, at Medium, claim and finish each message, as `cq dispatch` does for Codex. The turn gets one exchange folder that it can write, through `--add-dir`.
- **Exchange folder.** A Low label (no write up, inherited) and a protected DACL: the user and SYSTEM get Full control, the sandbox SID gets Modify. An existing folder must match as a set, or the watcher refuses it; its owner may be the user or the token's default owner (BUILTIN\Administrators when elevated). cq opens every path relative to a pinned folder handle and makes missing parent folders in the same walk, refuses reparse points, and reads `reply.json` only as a closed regular file with one link, capped at 64 KB, after every process of the turn has stopped. At start the watcher resolves the part of the exchange path that exists (Unix: `realpath`, so a symlink such as `/var` on macOS counts as it stands then; Windows: the final path of the pinned handle, so 8.3 names, case and `subst` drives give the real name), and the queue root too. The path rules apply to these resolved locations before any folder is made, and only the resolved path is used after that, in `--add-dir` and the prompt too. The walk then follows no link, and the exchange folder itself must not be one. Before each turn the watcher checks that the job folder path still leads to the pinned folder (same device and inode, or volume and file ID), and holds the job if not. A fatal watcher error during a turn stops the turn and holds the job.
- **Held handles have no delete access (Windows).** When agy's sandboxed shell starts, it opens the `--add-dir` folder and each folder above it without delete sharing, and adds an entry that lets the sandbox SID traverse it. A handle with delete access on any of those folders made that fail with a sharing violation (live test, 11 Nov 2026). So the watcher holds the exchange and job folders without delete access. Sharing, not access, stops a rename: the handles still deny delete sharing, so no folder of the path can be renamed or deleted while it is held, and the per-turn path check is unchanged. To delete a job folder, the watcher closes its handle, opens the folder again by name relative to the pinned exchange folder with delete access and without delete sharing, and deletes it only if the volume serial and file index match. The exchange folder check accepts that one added entry: access allowed, at most traverse and synchronize, not inherited and not inheritable, for the sandbox SID. It gives the sandbox less than its Modify entry and reaches nothing below the folder.
- **Unix trust boundary (not enough yet).** On Unix an open folder can still be renamed, so a path check alone cannot stop another process from swapping a folder of the path, and planting its own `request.json`, between the check and agy opening the request. The watcher therefore requires a trusted path, like OpenSSH's StrictModes: every folder from `/` down to the job folder must be owned by root or the watcher's user and not writable by group or others. A sticky folder (such as `/tmp`, mode 1777) may be, when the folder in it on the path is owned by root or the watcher's user, because the sticky bit stops others renaming that folder. The watcher checks this while it walks the path at start (before it makes any folder in one; exit 64 if not) and again, through the pinned descriptors, before each turn (the job is held if not). Processes that run as the same user or as root are inside the boundary: they can still change the path, as they can change the queue. The rule is not proof on its own: it reads only owners and mode bits, and a macOS extended ACL or a POSIX ACL can let another user add, delete or re-permission entries in a folder with mode 0755. Until the check reads ACLs, broker mode is refused on Unix. With the default exchange folder (inside the queue root), a queue root made with umask 002 (group-writable) is refused; give its folders mode 0755 or 0700. Windows needs no such rule: the pinned handles deny delete sharing, so no folder of the path can be renamed during a turn.
- **One rule for verdicts.** `decide()` maps a turn's verdict to a completion. Normal runs and restart recovery both use it, and `completion.json` must equal its result before `cq done` runs.
- **No retry and no reattach.** A turn that may have started is never run again, and a restarted watcher does not reattach to a running turn: the job is held for a person. Only a spawn failure is retried, because the child starts suspended and no `agy` code has run.
- **Not in 1.15.0.** `cq session-start` has no broker variant: the members record has no broker flag, and Antigravity does not run that hook.

## Antigravity session mode

Windows only in 1.17.0 (issue #104). `cq watch --to-agy-session` wakes an open Antigravity session (CLI or App) with `agentapi send-message`, through the broker's exchange folder and job record. Usage is in [Antigravity session mode](agents/ANTIGRAVITY.md#session-mode).

- **Why from inside.** agentapi needs the language-server address and a CSRF token that Antigravity gives only to processes it starts. So the session starts the watcher itself, once, as a background command with the sandbox bypassed by a saved `command(...)` rule. A watcher outside the session cannot wake it.
- **Little on the command line or in the environment is trusted.** The session writes the command line. So the line takes only `--as` and `--takeover`; the root is the build's `CQ_DEFAULT_ROOT`; every setting comes from `[agy-session.NAME]` in `config.toml`, and `CQ_ROOT` and other settings from the environment are ignored. The allowed senders never come from the environment. Three variables are read: the address, an agentapi path that may only confirm the launcher's image, and `ANTIGRAVITY_CONVERSATION_ID`. The conversation ID comes from that variable because Antigravity sets it and the session cannot change it: each run-command call is a fresh process, and the tool has no environment parameter (live test S1 environment). The table's optional `conversation` is the fallback when it is missing, and must match it when both are set.
- **The root must be out of the sandbox's reach.** Before any queue write the watcher pins the root, `config.toml` and `cq.exe` and walks each path from the volume root: no reparse point, no Low label, no write grant, direct or inheritable, to any app-container or capability SID (listed or not), the Low SID, a restricted-token SID or the policy's sandbox SID. A live test found a root whose DACL gave a capability SID inheritable Modify, so the sandboxed shell could write the queue; the policy's SID alone would have missed it. Ordinary principals pass, so a named sandbox group (an ordinary local group) is not caught: that, and keeping the queue root and `cq.exe` out of every agent workspace, with the CLI's `allowNonWorkspaceAccess` off (the file tool runs outside the OS sandbox, so ACLs do not bind it), are setup rules. cq does not read Antigravity's settings in v1. `config.toml` is read twice, before and after the policy SIDs are known, and must not change. The root folders stay held for the watcher's life.
- **The launcher, not the variables, is the anchor.** The watcher walks its parents (each must have started before its child) to the nearest `agy.exe` or `language_server.exe`, and runs that image's `agentapi`. `ANTIGRAVITY_AGENTAPI_EXE` may only confirm it. The image gets the `cq.exe` checks and stays held, with its folders, without write or delete sharing, so its path cannot be swapped while the watcher runs; before each wake the path must still open the same file (file ID), else exit 8 and a full check on the next start. A handle with no data access does not take part in sharing, so the held image is opened for execute. The address must be loopback, and every listener a connect could reach must belong to that process, checked again before each wake.
- **Exactly-once start.** The session creates `started` as a new file before it reads the request; if it exists, it stops. The watcher records each wake durably before it sends it, never sends NEW-WORK once `started` exists, and sends RESUME at most once. A wake that may have been lost is resent only while `started` is missing.
- **Liveness without a turn process.** There is no child to wait for. The watcher treats the session as gone when the launcher exits, when 3 connects to the address fail in a row, or when agentapi fails 4 times in a row, and then exits 8 so the session can start it again. It checks on every tick, also with no job, asleep or under `PAUSE`, so a watcher whose session has gone never holds the name. Sleep and `PAUSE` both hold every wake and every deadline. A restart holds (needs review) a `waking` or `woken` job whose message is no longer claimed, as it does `claimed` and `prepared` ones, so a message finished while no watcher ran is never woken again. In the App one language server serves many conversations, so a closed conversation shows up only as a missing `started` (exit 8 after `ack_minutes`).
- **The request carries the reply shape.** A live run showed a session that wrote a reply with no `status`, because only the outcome names were in `request.json`. So `request.json` has `reply_format`: fixed text from cq with the exact JSON of each offered outcome, filled only with the job's `id` and `nonce`, and both wakes say to copy it. The field made the request `cq-agy-request/2`; `/1` stays as it was, so strict readers of either version keep working. The broker mode's request has it too. Compatibility: a print-mode job from cq 1.15 or 1.16 may have a `/1` request when it recovers, and works, because its prompt does not use `reply_format` and recovery never reads the request. Session-mode jobs exist only from this version, so a restart holds (needs review, no wake, no rewrite) a session job whose request is not `/2`.
- **A restart keeps the deadlines; only a hold restarts them.** The record holds absolute deadlines, and a plain restart (a crash, a stop, a takeover) keeps them: a `waking` job past its ack deadline exits 8 again with no NEW-WORK, a `woken` job past its reply deadline gets the due RESUME, and one past the RESUME window needs review. A deadline that runs out while the name is asleep or under `PAUSE` starts again when the hold ends, also when the watcher started during the hold. So an expired round never restarts by accident, and a person who wants a new round asks for it: sleep or `PAUSE`, start the watcher, then wake or remove `PAUSE`. The cost: until then, each plain restart of that watcher exits 8. So that exit 8 gets its own stop line, which ends "Do not restart; tell the user." after the steps, and "Start the watcher again with the same line" stays for a gone session only; otherwise a session that follows the rules would restart in a loop.
- **The token is not a secret from the session.** The sandboxed shell already has it. cq never prints, logs or records it or the address, and passes it only to the agentapi child, with a minimal environment.
- **A wake is not an interrupt.** A live test showed that a wake during a turn arrives in that turn at the next tool-response boundary and cancels nothing. So a NEW-WORK text can reach a busy session; the exclusive `started` file keeps it to one start.
- **Open gates.** S1 writes (nothing the session runs can write the root, `config.toml` or `cq.exe`) failed on a misconfigured root and must pass on a fixed one, and the watcher still needs an end-to-end live run. See [Open gates](agents/ANTIGRAVITY.md#open-gates).

## Sleep

Stage 1 of [issue #7](https://github.com/niklasrichardson/session-queue/issues/7): manual sleep and wake for one session. The protocol is in [Protocol](PROTOCOL.md#sleep-and-wake).

- **Why a flag file.** `sleep/<name>` works like `PAUSE`, but for one name. A file needs no running process, survives restarts, can be checked by any `cq` command and by `cq-top`, and can be removed by hand. The watcher checks it on every 250 ms tick, so a running watcher stops within a second. A message to the session would not work: a stopped watcher cannot read it.
- **Its own exit code.** Exit 7 tells the session "do not re-arm". Exit 0 means "re-arm", and exit 5 means "retry with `--takeover`".
- **At start, no lock.** A watcher that finds its name asleep at start exits before it takes the lock or writes a heartbeat, pid file or members record. So it cannot replace a running watcher's record.
- **`CQ-SLEEP` under `PAUSE`.** The watcher prints `CQ-SLEEP` even while `PAUSE` exists. Otherwise a paused, sleeping watcher would run to `--max-seconds`, exit 0 and be re-armed for nothing.
- **Who may sleep whom.** Sleeping another session stops its work, so only a coordinator listed in `coordinators` may do it. Waking costs only tokens, so any name may wake any name (owner decision, 28 Oct 2026).
- **Waking comes from outside `cq`.** A sleeping session runs no `cq` process. The sender wakes it through Claude Code (the `/cq-start` skill), not through the queue. `cq send` still delivers, so nothing is lost, and warns, so the sender knows to wake the receiver.
- **`CQ-WAKE` is a backup.** A coordinator's watcher reports a message only after it has waited 2 minutes (`WAKE_AFTER`), so the sender has time to wake the receiver first. The age is the file's modified time, as for the prune. The coordinator scans every second, not on file events, and never claims or moves a message. It reports each message once per run, so a restarted coordinator reports old ones again, once. It is silent under `PAUSE`.
- **When sleep pays off.** Waking a session writes its whole context to the prompt cache again, which costs about 2 times the context in input tokens. Staying awake costs about 0.4 times the context per hour in re-arms and cache reads. So sleep pays off only for an idle period of about 5 hours or more, unless the context is small. These figures are for Monitor mode. In inbox mode, an idle session takes no re-arm turns, so staying awake costs less, and sleep pays off only after a longer idle period.
- **Not in stage 1:** automatic sleep after an idle time. `cq dispatch` (Codex) does not check the flag.

## Locks

[Issue #99](https://github.com/niklasrichardson/session-queue/issues/99): named locks, such as one for the desktop that GUI tests drive. The commands are in [Commands](COMMANDS.md#locks).

- **A file per lock, made by an exclusive create.** `take` opens `locks/<lock>.lock` with create-new, which the file system grants to one caller only, on Windows, macOS and Linux. No OS lock is held while the lock is held, so a lock survives the process that took it: a session takes it with one command and releases it with another. An OS lock would end with the process.
- **Release and break under a guard.** Release reads the holder and then removes the file. Without a guard, a break and a new take between those two steps would let the old holder remove the new holder's lock. Release and break hold the OS lock on `locks/<lock>.guard` for both steps. Take holds it from the create until the write is flushed, or until a failed write's file is removed, so that removal never hits a new holder's file; the create still decides which take wins. The guard file is never removed, so two processes never lock different files of the same name.
- **A half-written file.** A reader can find the file after the create and before the write. It reads again for up to half a second before it counts the file as unreadable (holder `?`). An unreadable file still holds the lock: removing it would need a guess about whether its taker is alive.
- **The holder is a queue name.** `--as` must pass the queue-name rule, as for `cq send`. When this session's key is in `members/` for another name, the command is refused, so a session cannot take or release under another session's name by mistake. There is no list of names that exist, so the check cannot do more without `members/` (send has the same limit).
- **The owner hold.** The user is not a queue name. A coordinator takes and releases the reserved holder `owner` for the user with `--owner`, so the user can claim the desktop from any coordinator session. Any coordinator may release it, so the hold does not depend on one session staying alive. It is never orphaned or stale: the user's presence has no heartbeat.
- **Orphaned and stale are reports, not actions.** A holder whose watcher stopped may still be working: a watcher can stop while its session runs. So `cq` never breaks a lock; a coordinator's watcher reports, and the coordinator decides. Orphaned uses the watcher rule of `cq status` with a 90-second grace from the take, so a session that takes a lock before its watcher starts is not reported at once. Stale only applies to a live holder, so one lock is never both. A reader treats a pid file that names its own process as a dead watcher's (the process check above), except a coordinator's watcher reading its own pid file: that is itself, so its own old lock is stale, not live.
- **Once per take.** A report is keyed by the state, the lock and the take's ID (for an unreadable file, which file it is: its file index or inode, modified time and size, so a file made again under the same name is a new take), and kept in `heartbeat/<name>.lock-alerts` after delivery, as for `CQ-OVERDUE`. So a restarted coordinator does not repeat it, and a new take of the same lock is reported again.
- **Wait polls.** `cq lock wait` checks every 15 seconds whether the file exists. File-system events would add a watcher per waiter for a wait that is measured in minutes. It sends no message, so a waiting session costs the holder nothing.
- **`PAUSE` refuses takes only.** Taking a lock starts new work, like `cq send`. Release, break, status, list and wait finish work or only read, so they still work.
- **`locks.log`** uses the same append and rotation as `watch-exits.log`, so lines from processes that end at the same time are kept whole.

## Codex dispatcher

- `dispatch` is a serial polling worker, not a Monitor replacement. One-second inbox scans find startup and later messages; it shares the watcher lock. A separate Codex process handles each task, with no prior conversation history.
- An explicit sender allowlist and a trusted local scope file are required. Sender names remain a soft filter. Queue bodies cannot select executables, flags or the scope file. Codex reads the target repository's AGENTS.md.
- The dispatcher invokes Codex directly, without a shell. Prompt data goes through a file on stdin. Structured final output carries status and reply. Event logs and stderr are files, so a full output pipe cannot deadlock a worker.
- Defaults are read-only sandboxing, no interactive approvals, ephemeral runs and invocation-local disabling of hooks and user configuration. A worker can explicitly select workspace-write. Existing saved authentication is reused.
- `dispatch/NAME/ID` retains prompts, output and completion records. The intended completion is written before `done`; incomplete records block restart. Records are not pruned automatically.
- Failures never replay a task. A crash near completion can make delivery uncertain, so there is no automatic retry, and an operator reviews side effects before recovery. Exactly-once side effects are not promised. What each failure does, and the recovery steps, are in [Failure handling and recovery](agents/CODEX-DISPATCH.md#failure-handling-and-recovery).
- The session membership key is the first non-empty CQ_SESSION_ID, CLAUDE_CODE_HOST_SESSION_ID or CLAUDE_CODE_SESSION_ID, with the existing sanitisation and 64-character cap. Codex variables are not read implicitly. The dispatcher does not register its parent chat, and clears inherited session IDs for each fresh child.

- The dispatcher reserves each job directory before claiming; a collision refuses the job without claiming the inbox message. It writes its PID while holding the watcher lock, removes its own PID on normal exit, and shares a single 30-second heartbeat schedule across idle scans, agent execution and PAUSE waits.
- When PAUSE appears during a task, the dispatcher retains its answer and waits before calling done. Interruption leaves the task claimed. PAUSE can still race with completion after the final check; a resulting exit 4 remains an operator recovery case.

- Claims take a separate OS lock at heartbeat/NAME.claim.lock for the move and validation transaction. Windows can otherwise report two successful renames when both callers opened the same source before it moved. The second claimant checks the inbox after the first transaction and exits 1. The lock file is retained; deleting it while held could let a new file bypass the lock.
